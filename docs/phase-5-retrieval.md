# Scoped retrieval and private readiness

Manager preview is `POST /dashboard/agents/{agent_id}/knowledge/search` with `query` (1–1000 characters after trimming), `language` (`en` or `ur`) and UUID `query_id`. Tenant authority comes from the authenticated manager; agent authority comes from the path. Extra scope fields are rejected. The response contains up to four bounded chunks and a reason, never a generated answer. `no_sources`, `processing_pending`, `below_threshold` and `service_unavailable` are distinct outcomes. Unavailable embeddings never fall back to a successful keyword-only response.

`KnowledgeService(factory, embeddings, *, audit_secret=settings.jwt_secret.get_secret_value()).retrieve(KnowledgeScope(...), query, language, *, query_id, deadline)` uses independent short transactions around embedding RPC. Source reads do not lock source rows; event writes do not retain source locks when the Agent foreign key is acquired. Authentication preflight also ends before the external call. Initial/event transactions have 3-second statement and 1-second lock limits; ranking is limited to the remaining deadline, capped at 5 seconds. Audit insertion can require its bounded transaction after the retrieval deadline.

The SQL materializes only the authorized agent's active, nondeleted, sealed, matching-profile corpus. It computes exact cosine and `simple` FTS ranks, takes dense20 and keyword20, sums reciprocal ranks with k60, gates every candidate on actual cosine >=0.55, and returns top4 with deterministic UUID tie handling. A 16,385th chunk is an overflow sentinel: no partial corpus is served. HNSW and GIN indexes remain installed; this path deliberately uses a bounded exact scan, so foreign or historical index entries cannot starve authorized recall. This entails linear vector work and materialization/temp I/O over up to 64×256 chunks. Synthetic capacity tests and query plans establish control behavior, not production latency or multilingual model quality.

Private retrieved refs retain both current Source.revision and Generation.source_revision. A new query may use the previous active generation while reindexing is queued or failed. Runtime final validation checks the captured current resource revision, active generation and profile before answering; comparing the generation's originating revision against the current source revision would incorrectly reject this supported state.

Query events retain a purpose-separated HMAC-SHA256 fingerprint of tenant/agent/question/language/purpose/session/test identity, purpose, language, decision, bounded IDs/revisions/scores, and duration. Raw questions are **always omitted** (`redacted_question = NULL`): name/label regexes cannot reliably prove arbitrary bilingual patient text safe. This includes known and unknown names, DOB, phone and identity factors. Events contain neither returned chunk text nor provider bodies. Same query ID with changed payload conflicts; concurrent identical events deduplicate. The audit key is `HMAC-SHA256(API JWT secret, "knowledge-query-key-v1")`; the fingerprint is `HMAC-SHA256(audit key, "knowledge-query-v1\0" + UTF8(compact JSON array))`. UUIDs use canonical string form; optional IDs use empty strings, language/purpose are validated, and both the manager and direct service use the established `RetrievalQuery` contract to strip surrounding question whitespace before enforcing the shared 1–1000-character limit. There is no Unicode normalization or case folding. The secret is never stored in events. JWT-key rotation makes previously recorded query IDs conflict instead of weakening verification. Grouped outcomes remain available, but representative question text requires a separately reviewed safe-text policy. Repeated previews may recompute current corpus results; this is event deduplication, not a cached answer replay.

## Readiness observations

`GET /internal/status` on the embedding service authenticates the existing embedding bearer and returns only `{profile, ready}`. It observes an already initialized supervisor; it never loads artifacts/tokenizers/models or infers. The client validates the exact profile and uses a 2-second wall deadline, bounded body and one outstanding status request, retaining its slot until a timed-out transport exits.

The enabled worker has an independent 10-second heartbeat thread. It probes its actual narrow database login, authenticated embedding readiness and exact tokenizer artifact size/SHA256 without loading the tokenizer. It writes `.worker-readiness.json` atomically with mode0600 on the existing private blob volume. The envelope is HMAC-SHA256 authenticated with the existing distinct blob secret and purpose prefix `knowledge-readiness-v1\0`. It contains protocol version1, exact profile, observation start timestamp and strict worker/embedding/artifacts booleans. Timestamping precedes probes; slow observations do not become newly fresh on completion. API verification rejects absent, malformed, wrong-key/profile, symlink, permissive-file-mode, future and >30-second-old records. Stopped workers may remain observed healthy only within that explicit freshness window. Configuration/enabled flags alone cannot establish processing readiness.

Capabilities expose separate `processing_available`/`unavailable_reason` and `query_available`/`query_unavailable_reason`. Ready-corpus query availability checks actual embedding status independently of the worker heartbeat. A missing blob secret disables processing observations and unsafe blob writes/cleanup, while text CRUD and indexed queries remain usable when their own prerequisites hold.

## Current local rollout boundary

The local API was refreshed at migration `0009`; see the [current checkpoint](phase-5-testing.md) and [results](phase-5-results.md). Earlier Task 4/5/7 stage evidence is historical. For a new deployment, provision a distinct `KNOWLEDGE_BLOB_SECRET` only to API (`SCHEDULER_KNOWLEDGE_BLOB_SECRET`) and worker (`KNOWLEDGE_WORKER_BLOB_SECRET`), over the same private volume. The API query RPC additionally uses `SCHEDULER_KNOWLEDGE_EMBEDDING_URL` and `SCHEDULER_KNOWLEDGE_EMBEDDING_SECRET`; Compose maps the latter from the existing `EMBEDDING_SECRET` and joins the API to the existing project embedding-private network for the current controlled rollout. The embedding container receives no blob key, database credential or volume. Native API defaults to the existing loopback8001 service URL. API and worker must share the same private blob directory for heartbeat evidence.

The local private configuration and API refresh are complete. Real BGE loading/inference, tokenizer qualification, multilingual retrieval quality and native voice acceptance remain deferred; embedding, worker and voice execution remain disabled. Runtime/test grounding and final answer validation are implemented. A ready development corpus and end-to-end RAG acceptance are not claimed. No migration, grant expansion, owner database mutation or service restart is required for unit verification.
